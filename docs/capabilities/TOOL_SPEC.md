# Tool specification for a 350M pet — 0.1 draft

Status: proposal draft (2026-09-10). This spec codifies the tool-call patterns already proven in `PaladinoAgent`, `NoteToolProtocol` and `PhoneReads`, so every new category scales the same way instead of inventing a new protocol per feature.

## Design constraints (why it looks like this)

LFM2.5-350M is the permanent target, and fine-tuning from usage is a product goal. That means:

1. **One tool per category**, not one tool per verb. `sms` handles read/send/search of messages; `calendar` handles today/insert/prepare. Fewer choices = higher selection accuracy at 350M scale.
2. **Single `argument` string per call** — the schema the parser and model already master. Verbs are expressed inside a tiny grammar, parsed deterministically (no free-form JSON objects to hallucinate).
3. **Deterministic routing first.** Explicit, templated requests ("what was my next alarm", "responde ao João") are handled by `PhoneReads`-style routers and never spend a model hop. The model only chooses tools for generative phrasing.
4. **Bounded everything.** Every call goes through `LoopBudget` (hops ≤4, calls ≤3, repeat-digest detection), per-category result caps (characters/rows), and the session byte-budget check.
5. **Manifest-gated.** A tool does not exist for a session unless (a) it is in the role manifest's `allowedTools`, (b) its `Capability` flag is granted in the three-way intersection, and (c) its category router/registry registers it. Privilege expansion is rejected at parse time.

## Tool-call grammar

Keep `NoteToolProtocol` as the reference implementation and generalize it:

```text
{"name":"<tool>","arguments":{"argument":"<verb> <payload>"}}
```

or LFM's Pythonic form `<tool>(argument="<payload>")` — both already parse. Payloads use `<verb> [qualifiers] :: <content>`:

| Tool | argument examples | Verbs |
|---|---|---|
| `notes` (exists as notes_search/notes_save) | `save :: bicycle is in the blue garage` · `find :: bicycle` | save, find, delete |
| `calendar` | `today` · `insert :: Dinner with Ana Friday 20:00` · `prepare :: ...` | today, range, insert, prepare, edit |
| `sms` | `inbox :: 5` · `search :: dentist` · `send :: +351… :: running late` · `draft :: +351… :: …` | inbox, search, send, draft, delete |
| `telegram` / `whatsapp` | `recent :: 10` · `share :: chat :: text…` | recent, search, share (handoff) |
| `device` (security) | `status :: vpn` · `apps :: risky` · `scan :: play-protect` · `orbot :: start` | status, apps, scan, orbot |
| `osint` | `breach :: user@example.com` | breach, audit |

Rules carried over unchanged from the existing parser: strict name allowlist per session, argument ≤12000 chars, no expression evaluation, one repair attempt, "repeated identical call stopped", and **cloud (Maxx) output is never parsed as a tool call**.

## Registration and gating (per session)

```kotlin
if (mode == TINY && options.toolCalls) {
    if (options.messagingRead && tools.smsRead != null)  tool(smsReadTool)
    if (options.messagingWrite && tools.smsSend != null) tool(smsSendTool)
    // each tool checks manifest.allowedTools again at execution time
}
```

- Each capability adds a `SessionOptions` flag pair (read/write) + `Capability` enum entry (the enum already reserves `FILES`, `NOTIFICATIONS`, `APP_ACCESS`, `WEB_SEARCH`).
- Runtime Android permissions are requested on first use through the existing `PhoneAccessCard` settings surface, never mid-conversation.
- Every execution logs `tool_call` / `tool_result` (bounded detail) to `execution_events` — the quest log/audit trail — with content kept in-session, per current policy.

## Approval binding

Writes reuse `ActionProposal` + `ApprovalPolicy` verbatim: extend the `allowed` set with the new tool IDs (`sms.send`, `calendar.insert`, `device.orbot`, …), keep the 5-minute expiry, keep the `tool\u0000argument` hash check, keep transactional execution with truthful reporting back to the model ("user declined. Nothing was sent."). Handoffs (share sheet, dialer, calendar insert UI, Play Protect, VPN settings) are *proposals whose result is reported as "handed off"*, never as success of the external action.

## Result shaping for small context

- Every category read returns a capped, pre-rendered block (today ≤20 events; inbox ≤5 threads × N messages; scan report ≤10 apps) with a fixed header so the model doesn't reformat arbitrarily.
- Long content is summarized *before* entering context when over budget (local embedder/classifier first; cloud summarization only via approved `summarize_context` purpose).
- Numeric/structured answers are computed deterministically and handed to the model as data, never generated by arithmetic in the model.

## Evaluation contract (same bar as the existing suites)

Any new category ships with: JVM router/parser tests (EN/PT), invalid/unapproved-action block tests (100% block), real-model held-out argument checks on the emulator lane, and updated `docs/evidence/`. Targets inherited from MISSING-01/02: ≥95% correct arguments on unambiguous in-scope requests; routing macro-F1 ≥0.90 once semantic routing lands.
